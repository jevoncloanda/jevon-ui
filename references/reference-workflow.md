# Interpret visual references

Use for screenshot, Figma, live-site, or multiple-reference work. Apply the design authority in [SKILL.md](../SKILL.md); references do not override an explicit project specification unless the user changes that authority.

1. Inspect every supplied reference through available tools. If one is inaccessible, state what cannot be established rather than pretending to have inspected it; continue with evidence available and request access when necessary.
2. Identify each reference's intended influence. Honor explicit scopes. For example: A governs navigation, B table density, C typography, and D interaction hierarchy. Where scope is unclear and mixing would materially change identity, clarify it.
3. Extract relevant layout, hierarchy, density, typography, spacing, component treatment, navigation, and interactions. A static screenshot does not prove interaction behavior; inspect a live flow or mark assumptions.
4. Translate those characteristics into the current product's tokens, components, data, states, and supported viewports. Resolve conflicting references by authority and scope, not by blending every feature.
5. Compare the rendered implementation with each reference only within its intended scope. Check that the adaptation still supports the product's actual workflow.

Do not blindly copy third-party branding, copyrighted imagery, product-specific copy, or an exact composition unsuitable for this product. Use supplied or authorized assets according to the user's intent. For a deliberately close implementation, preserve the requested layout fidelity while adapting content and assets appropriately.

Keep a short reference-to-decision mapping in the preflight or existing design documentation when useful. Do not create a separate reference dossier for a small change. Impeccable can help with unresolved shaping/design questions; it must not reinterpret a precise reference as permission to invent a new visual world.
